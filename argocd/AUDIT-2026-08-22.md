# Argo CD audit — 2026-08-22

## Статус документа

Это снимок полного статического и live-аудита runtime/GitOps слоя на
2026-08-22. Исходные наблюдения сохранены ниже как evidence до remediation;
актуальный результат выполнения плана зафиксирован в следующем разделе.

Проверенный live GitOps snapshot: `717edfd6957d0f79fb3826c1ca31d45b72e53dbc`.
Локальный repository HEAD на момент аудита: `90d1457` с незакоммиченными
изменениями, включая 18 изменённых или новых файлов в `argocd/`.

Во время аудита live-кластер не изменялся. Secret values, OpenBao tokens и
recovery material не читались и не сохранялись.

## Результат выполнения плана — 2026-08-22

После исходного read-only аудита был выполнен controlled remediation с
сохранением ownership boundaries: runtime changes остались в `argocd/`, Argo
CD Helm/OIDC/RBAC — в `infrastructure/`, runtime credentials — в OpenBao с
доставкой через ESO. Секретные значения в Git и вывод команд не попадали.

Итоговый live snapshot Argo CD: `a9e205ee1f7f9af7f219a0d87becfdfe052ae083`.
Все 37 Applications имеют `Synced/Healthy` и включённый automated sync.

  credentials сохранены в OpenBao; BSL `default` имеет `Available`; backup

## Резюме

Статическая структура GitOps слоя консистентна: 33 platform Applications
индексируются ровно один раз, environment/version/secret contracts сходятся,
Kustomize и observability Helm render проходят. Все live PVC имеют состояние
`Bound`, существующие ExternalSecrets — `SecretSynced`, Certificates —
`Ready`, Gateway и HTTPRoute — `Programmed`/`Accepted`.

При этом live-состояние нельзя считать готовым:

- все 422 объекта Velero Backup имеют фазу `FailedValidation`;
- BackupStorageLocation `default` недоступен;
- Garage layout не инициализирован;
- Tempo не развёрнут, а OTel Collector теряет трейсы;
- Harbor остаётся `OutOfSync` после неуспешной синхронизации;
- live Argo CD не получил ожидаемые OIDC и RBAC настройки;
- локальные исправления observability ещё не опубликованы;
- Kyverno фиксирует нарушения security baseline, а policy и NetworkPolicy
  coverage остаются неполными.

## Замечания

### P0 — восстановление данных и telemetry

#### A-01. Резервное копирование полностью неработоспособно

Наблюдения:

- `BackupStorageLocation/default` имеет фазу `Unavailable`;
- endpoint `https://minio.lab.zerodi.ru` возвращает TLS certificate для
  случайного Traefik/default hostname, а не для `minio.lab.zerodi.ru`;
- оба Velero Schedule включены, но успешных Backup нет;
- все 422 Backup имеют фазу `FailedValidation`;
- PodVolumeBackup отсутствуют.

Следствие: кластер не имеет подтверждённого GitOps-managed backup/restore
контура. Наличие Schedule не является доказательством защиты данных.

#### A-02. Garage не готов как S3 backend

`garage status` показывает single-node instance с состоянием
`NO ROLE ASSIGNED`. Layout, bucket и production S3 key не созданы. Это
предусмотренный ручной этап, но он не был завершён.

#### A-03. Трейсы теряются

Live Application `tempo` имеет `Unknown/Healthy` и `ComparisonError`: старый
`tempo-distributed 3.0.6` требует Kafka для block builder/live store. Tempo
Pods, Service и PVC отсутствуют.

OTel Collector продолжает экспорт в отсутствующий Tempo, сообщает
`sending queue is full`, `Dropping data`, `no more retries left` и DNS errors
для старых `tempo-distributor`/`tempo-query-frontend` endpoints.

Локально подготовлен переход на single-binary chart `tempo 2.2.4`, но он ещё
не опубликован и не проверен live.

### P1 — GitOps convergence и доступ

#### A-04. Live GitOps snapshot отстаёт от рабочего дерева

Root и большинство дочерних Applications синхронизируют snapshot `717edfd`.
Локальные изменения включают новую Tempo topology, `otel-agent`, Grafana
alerting secret, observability NetworkPolicy, metrics collection и security
настройки. Эти ресурсы нельзя считать внедрёнными.

Публикация также заблокирована рабочим процессом репозитория: `task gitops:push`
намеренно откажется работать при незакоммиченном `argocd/` subtree.

#### A-05. Harbor не достигает желаемого состояния

Application `harbor` имеет `OutOfSync/Healthy`. Последняя sync operation
завершилась ошибкой strategic merge patch list order для
`StatefulSet/harbor-trivy`; `Secret/harbor-core` также отображается
`OutOfSync`.

`Healthy` здесь означает, что старые Pods продолжают работать, а не то, что
live соответствует Git.

#### A-06. OIDC и RBAC Argo CD не внедрены live

Live `argocd-cm` не содержит `oidc.config`; live `argocd-rbac-cm` содержит
пустые `policy.csv` и `policy.default`. В то же время repository
`infrastructure/argocd.tf` задаёт Authentik OIDC, group mapping и default
role. Следовательно, desired infrastructure config и live release расходятся.

`argocd-initial-admin-secret` всё ещё существует. До подтверждения SSO и
break-glass доступа удалять или отключать admin нельзя.

#### A-07. Не материализованы обязательные runtime resources

Live отсутствуют:

- `authentik/Secret/platform-identity-blueprint`;
- `argocd/Secret/argocd-oidc`;
- `harbor/Secret/harbor-oidc-config`;
- `observability/Secret/grafana-oidc`;
- `observability/Secret/grafana-alerting`;
- Application `otel-agent`.

Существующие ExternalSecrets исправны. Это GitOps revision gap, а не отказ
ESO/OpenBao. Полный OpenBao preflight во время аудита не выполнялся, потому
что локальный port-forward на `127.0.0.1:8200` не был запущен.

### P2 — security и isolation

#### A-08. Kyverno подтверждает нарушения workload baseline

Live PolicyReports фиксируют:

- Harbor: отсутствующие security context и requests/limits;
- Harbor PostgreSQL/Valkey: mutable `latest` images и security context gaps;
- Echo и Garage: неполный container security context.

У Garage security context отсутствует в repository StatefulSet. У Echo задан
pod-level seccomp, но не заданы обязательные container-level
`runAsNonRoot`, `allowPrivilegeEscalation: false` и `capabilities.drop: ALL`.

#### A-09. Policy coverage неполный

Policies для security context и requests/limits работают только в режиме
`Audit`. Из них исключены многие platform namespaces, включая `argocd`,
`authentik`, `forgejo`, `observability` и `velero`. Поэтому успешный Argo CD
sync не означает прохождение security baseline.

#### A-10. Mutable и transitive images не контролируются полностью

Repository явно использует `bitnami/kubectl:latest`. Live Bitnami
PostgreSQL/Redis/Valkey workloads также используют `latest`.

Текущий `check:versions` подтверждает согласованность объявленных pins, но не
запрещает `latest` и не анализирует все images, сгенерированные Helm charts.

#### A-11. NetworkPolicy coverage недостаточен

Live NetworkPolicy отсутствует в `observability` и `woodpecker`. Полноценного
namespace default-deny baseline нет для Authentik, Forgejo, Harbor, Garage и
Woodpecker.

Подготовленная локальная observability policy всё ещё широка: она разрешает
Grafana/OTLP ingress из любого namespace и весь межnamespace egress. DNS rule
при таком egress становится практически избыточным.

#### A-12. Argo CD использует plaintext для части внутрикластерных соединений

Infrastructure values включают `server.insecure`, plaintext repo-server
connections и отключённый repo-server TLS. NetworkPolicy ограничивает доступ
к repo-server, но `argocd-server` разрешает ingress от любых Pods и не имеет
egress restriction.

#### A-13. AppProject `platform` имеет большой blast radius

Project разрешает любые namespaced resources, а также Namespace, CRD,
ClusterRole, ClusterRoleBinding, ClusterIssuer, GatewayClass и cluster-wide
policies. Один project объединяет все platform domains и множество внешних
Helm repositories.

#### A-14. Git revision и автоматизация увеличивают риск публикации

Root и дочерние Applications используют mutable `targetRevision: main` вместе
с автоматическими `prune` и `selfHeal`. Ошибка в опубликованном subtree может
автоматически распространиться на весь runtime слой.

### P3 — reliability и verification

#### A-15. Argo CD не имеет HA baseline

Live развёрнуты по одному application-controller, server, repo-server и Redis.
Для homelab это допустимый компромисс, но потеря соответствующего worker или
плановое обновление временно остановит reconciliation/UI.

#### A-16. Post-deploy audit даёт неполную гарантию

`task ops:post-argocd-check` пока не проверяет:

- фазу BackupStorageLocation и возраст последнего успешного Backup;
- Garage layout/bucket readiness;
- наличие и readiness Tempo workload/PVC;
- ошибки или drop counters OTel exporters;
- Kyverno PolicyReport failures;
- live OIDC/RBAC configuration Argo CD;
- соответствие ожидаемому GitOps snapshot.

Поэтому большая часть Applications отображается `Healthy`, когда backup и
tracing фактически не работают.

#### A-17. Validation покрывает Helm charts неравномерно

Есть отдельный Helm render check для observability, но аналогичного полного
render/policy validation нет для Harbor, Forgejo, Authentik, Woodpecker,
Velero и их Bitnami dependencies. Это позволяет пропустить неэффективные
values keys, transitive `latest` images и missing security/resources.

#### A-18. Неблокирующие YAML warnings

Yamllint прошёл с десятью предупреждениями о строках длиннее 160 символов в
Grafana values и Forgejo SSO Job. Функциональной ошибки нет, но такие строки
ухудшают review и сопровождение embedded JSON/scripts.

## План исправления

План рассчитан на greenfield ownership model репозитория. Runtime manifests
остаются в `argocd/`, Argo CD Helm release и его OIDC/RBAC config — в
`infrastructure/`, secrets — только в OpenBao с доставкой через ESO.

### Этап 0. Зафиксировать безопасную точку изменения

Цель: исключить случайную публикацию смешанного рабочего дерева.

1. Разделить текущие изменения на логические наборы: observability,
   application metrics/security, audit tooling и документация.
2. Проверить diff каждого набора на secret values и несвязанные изменения.
3. Закоммитить `argocd/` только после прохождения локальных checks.
4. Зафиксировать ожидаемый GitOps commit/snapshot для последующей live-проверки.

Проверки:

```bash
task check:env-contract
task check:versions
task check:runtime-secret-contract
task check:kustomize-bootstrap
task check:kustomize-platform
task check:helm-observability
task check:yamllint
```

Критерий готовности: `argocd/` clean, публикация содержит только проверенные
runtime changes, secret values отсутствуют.

### Этап 1. Восстановить Garage и Velero

Цель: получить хотя бы один проверенный backup до остальных рискованных
rollout/recreate операций.

1. Определить канонический Velero S3 endpoint. Для внутрикластерного consumer
   использовать `http://garage-s3.garage.svc.cluster.local:3900`, если внешний
   TLS endpoint не нужен по архитектурному контракту.
2. Если внешний endpoint сохраняется, исправить DNS/Gateway routing и
   подтвердить certificate chain для `minio.lab.zerodi.ru`.
3. Получить Garage node ID и вручную назначить single-node layout согласно
   `docs/garage-velero.md`.
4. Создать bucket `homelab-velero` и S3 key `velero`, выдать минимальные права.
5. Записать production credentials в `secret/platform/velero/s3`, не выводя
   их в Git, logs или shell history; удалить provisional marker штатной
   перезаписью OpenBao path.
6. Дождаться ESO refresh и состояния BSL `Available`.
7. Создать smoke backup namespace `echo`, дождаться `Completed`.
8. Выполнить restore smoke-test в отдельный временный namespace и проверить
   восстановленные объекты.
9. Добавить alert на недоступный BSL и отсутствие свежего успешного backup.

Критерий готовности: BSL `Available`, новый Backup `Completed`, restore test
успешен и задокументирован.

Ручные границы: layout, bucket/key, OpenBao writes и restore требуют явного
операторского подтверждения. Удаление test namespace — отдельная destructive
операция.

### Этап 2. Опубликовать и восстановить observability

Цель: прекратить потерю telemetry и внедрить подготовленные изменения.

1. Перед публикацией проверить OpenBao contract для Grafana admin, OIDC и
   alert webhook; не выводить значения.
2. Повторно отрендерить Tempo, OTel Collector, OTel Agent, Loki и Grafana.
3. Проверить generated manifests на PVC, probes, service account token,
   security context, resources и ожидаемые service ports.
4. Опубликовать отдельный observability commit через штатный `gitops:push`.
5. Дождаться `Synced/Healthy` для `observability-prereqs`, `tempo`,
   `otel-agent`, `otel-collector`, `loki`, `victoria-metrics`, `grafana`.
6. Проверить Tempo PVC, OTLP ingest, trace query из Grafana и отсутствие
   exporter queue drops.
7. Проверить Grafana dashboards, provisioned alert rules и тестовую доставку
   webhook notification.

Критерий готовности: тестовый trace доступен в Grafana/Tempo, OTel drop/error
counters не растут, alert delivery подтверждена.

### Этап 3. Восстановить identity chain и Argo CD access

Цель: привести live Argo CD к declarative OIDC/RBAC contract без потери
break-glass доступа.

1. Запустить OpenBao port-forward и выполнить полный `task gitops:preflight`.
2. Убедиться, что paths `platform/argocd/oidc`, Authentik platform identity,
   Harbor OIDC и Grafana OIDC содержат ожидаемые keys.
3. Опубликовать/sync соответствующие ExternalSecrets и Authentik blueprints.
4. Дождаться `Secret/argocd-oidc` и успешного применения Authentik provider.
5. Выполнить `tofu -chdir=infrastructure plan` и проверить только ожидаемые
   изменения Argo CD Helm release.
6. После отдельного разрешения применить infrastructure plan.
7. Проверить `oidc.config`, RBAC mapping группы `platform-admins` и успешный
   SSO login.
8. Проверить local admin/break-glass доступ, ротировать пароль и только после
   этого удалить `argocd-initial-admin-secret`.

Критерий готовности: SSO работает, пользователь вне admin group не получает
admin, `platform-admins` получает ожидаемую роль, break-glass проверен,
bootstrap secret отсутствует.

### Этап 4. Исправить Harbor convergence

Цель: получить `Synced/Healthy` без потери registry/trivy данных.

1. Отрендерить Harbor chart с текущими values и сравнить desired/live
   `harbor-trivy` StatefulSet и `harbor-core` Secret metadata без чтения
   secret data.
2. Найти дублирующиеся или меняющие порядок env/volumeMount list entries и
   устранить их на уровне values.
3. Не маскировать ошибку постоянным `ignoreDifferences`, пока причина patch
   order не устранена.
4. Сначала выполнить server-side dry-run/diff.
5. Если требуется controlled recreation StatefulSet, подтвердить сохранность
   PVC и наличие успешного backup из этапа 1; запросить отдельное разрешение.
6. Sync Harbor и проверить core, registry, jobservice, portal, Trivy, push/pull
   smoke-test и OIDC login.

Критерий готовности: Harbor `Synced/Healthy`, sync history успешна, registry
push/pull и Trivy работают.

### Этап 5. Закрыть security и image gaps

Цель: получить нулевое число новых baseline violations в управляемых
workloads.

1. Заменить `bitnami/kubectl:latest` на immutable version или digest.
2. Явно pin все Bitnami workload/exporter images, которые charts сейчас
   рендерят как `latest`.
3. Добавить полноценный container security context в Echo и Garage.
4. Для Harbor задать component-specific security/resources values и
   подтвердить их по rendered Pods, а не только по values file.
5. Добавить resources/security context для init containers и sidecars.
6. Расширить policy audit на platform namespaces с документированными точечными
   исключениями.
7. После нулевого/принятого набора violations переводить security/resource
   policies из `Audit` в `Deny` поэтапно.

Критерий готовности: rendered и live workloads не используют `latest`, новые
PolicyReports не содержат необъяснённых failures, rollout не блокируется
Kyverno.

### Этап 6. Ввести namespace network isolation

Цель: перейти от выборочных policies к default-deny и явным service flows.

1. Составить матрицу ingress/egress для каждого namespace.
2. Добавить default-deny ingress/egress в Authentik, Forgejo, Harbor, Garage,
   Woodpecker и Observability.
3. Разрешать Gateway traffic по namespace/pod labels, а не из любого
   namespace.
4. Ограничить observability ingress конкретными producers и Gateway; убрать
   unrestricted inter-namespace egress.
5. Явно разрешить DNS, Kubernetes API, OpenBao/ESO, database/cache,
   OTLP/metrics/logs и необходимые внешние HTTPS/SMTP endpoints.
6. Проверять policies по одному namespace с connectivity smoke-tests.

Критерий готовности: default-deny действует, все задокументированные потоки
работают, неожиданный cross-namespace connection блокируется.

### Этап 7. Уменьшить blast radius Argo CD

Цель: ограничить последствия компрометации Git/Helm source или ошибочного
commit.

1. Разделить `platform` AppProject минимум по cluster-scoped bootstrap и
   namespaced runtime domains.
2. Сузить destinations и namespace resource whitelist каждого project.
3. Оставить CRD/ClusterRole/ClusterRoleBinding только Application, которым они
   действительно нужны.
4. Рассмотреть immutable Git revision для release promotion вместо прямого
   auto-sync `main`.
5. Добавить sync windows или staged promotion для storage, identity и policy
   changes.
6. Оценить включение TLS для внутренних Argo CD connections; если plaintext
   сохраняется, сузить server/repo-server NetworkPolicies.
7. Зафиксировать решение по single-replica/HA baseline для homelab.

Критерий готовности: каждый Application имеет минимально необходимые source,
destination и resource permissions; критические изменения не попадают live
одним непроверенным push.

### Этап 8. Расширить автоматические проверки

Цель: сделать live audit доказательством работоспособности, а не только
наличия Kubernetes objects.

Добавить в repository checks:

1. Helm render всех runtime charts и их dependencies.
2. Проверку rendered images на `latest`/missing tag и опционально на digest.
3. Policy validation rendered Pods для resources/security context.
4. Проверку BSL `Available`, свежего `Completed` Backup и результата
   периодического restore test.
5. Проверку Garage layout/bucket readiness без вывода credentials.
6. Проверку Tempo health, PVC и synthetic trace round-trip.
7. Проверку OTel exporter failure/drop counters.
8. Проверку Kyverno PolicyReports с allowlist принятых исключений.
9. Проверку Argo CD OIDC/RBAC config и bootstrap secret lifecycle.
10. Проверку ожидаемого GitOps snapshot/revision.

Критерий готовности: `task ops:post-argocd-check` падает на каждом из
состояний A-01—A-07 и предоставляет короткую причину без secret values.

## Общая последовательность выполнения

```text
clean/validate changes
  -> Garage layout and working Velero backup/restore
  -> publish observability and stop trace loss
  -> materialize identity secrets and apply Argo CD OIDC/RBAC
  -> fix Harbor convergence
  -> image/security remediation
  -> namespace NetworkPolicy rollout
  -> AppProject/Argo CD hardening
  -> expand CI and live audit gates
```

Этапы, меняющие live cluster, выполняются только после review diff/plan и
явного разрешения. Storage recreation, restore, secret writes, admin secret
deletion и Garage layout остаются отдельными operator checkpoints.
